# 智能药盒 · 微信小程序端

基于**华为云 IoTDA** 的智能药盒系统，软件部分包含微信小程序、本机中转服务和设备数据协议。
硬件侧（ESP32 + HX711 称重 + OLED + 蜂鸣器）由另一位同学负责，通过 MQTT 与本项目对接。

## 系统架构

```
┌─────────────┐   HTTP    ┌──────────────┐  V11-HMAC-SHA256  ┌─────────────┐
│  微信小程序  │ ────────▶ │  本机中转服务 │ ────────────────▶ │ 华为云 IoTDA │
│  (3 个页面)  │ ◀──────── │  (Node.js)   │ ◀──────────────── │  设备影子    │
└─────────────┘           └──────────────┘                   └──────┬──────┘
                                                                    │ MQTT 1883
                                                             ┌──────▼──────┐
                                                             │  ESP32 药盒  │
                                                             └─────────────┘
```

小程序**不能直连华为云**：AK/SK 放在前端会被反编译获取，且小程序请求域名需备案。
因此中间加一层本机 Node 服务，由它完成签名和 API 调用。

## 目录结构

```
.

│  ├─ pages/records/         记录：按日期分组，带服药状态标签
│  ├─ utils/api.js           接口封装（BASE_URL 需改成你电脑的局域网 IP）
```

## 快速开始

### 1. 配置中转服务

```bash
cd server
copy config.example.js config.js     # macOS/Linux: cp
```

编辑 `config.js`，填 4 个值：

| 变量 | 从哪获取 |
|---|---|
| `AK` / `SK` | 华为云控制台 → 我的凭证 → 访问密钥 |
| `PROJECT_ID` | 我的凭证 → 项目列表 → `cn-north-4` 那一行 |
| `PREFIX` | 设备接入地址最前面那段，如 `382f09a250` |
| `DEVICE_ID` | 控制台设备详情页 |

`config.js` 已加入 `.gitignore`，**不会也不应该提交到仓库**。

### 2. 自检

```bash
node check.js
```

依次验证配置、签名、设备查询、属性读取。任一步失败会打印华为云原始错误和排查建议。

### 3. 启动

```bash
node server.js
# 或 Windows 双击 start-server.bat
```

启动后打印局域网地址，把它填进 `miniprogram/utils/api.js` 的 `BASE_URL`。

### 4. 导入小程序

微信开发者工具 → 导入项目 → 目录选本仓库根目录 → AppID 填 `wx7d45b3a8751dcbde`
→ 详情 → 本地设置 → 勾选「不校验合法域名」（服务走 http，不勾会被拦）。

## 没有硬件时：虚拟设备

`server/device-sim.js` 是一个用 Node 手写的 MQTT 客户端，扮演真实药盒的角色：自动连华为云、
订阅命令主题、**收到命令 0.1 秒内自动回执**（真实固件也必须在这个量级回执，平台 20 秒就判超时）。

```bash
cd server
node device-sim.js --report                        # 连上并上报一次属性
node device-sim.js --report --dose --taken=1       # 再模拟一次"服药完成"
```

参数：`--report` 上报属性、`--dose` 发一次服药事件、`--plan=HH:MM` 指定计划时间点、`--taken=N` 今日已服次数。

**注意**：华为云同一设备只允许一个 MQTT 连接。虚拟设备运行时，MQTT.fx 和控制台「在线调试」都会抢占失败，
用之前先让对方断开。

## 接口

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/ping` | 存活检测 + 局域网 IP |
| GET | `/api/status` | 设备在线状态 + 影子属性 + 当前计划 + 已归档记录（顺带归一次事件） |
| GET/POST | `/api/plan` | 读取 / 下发服药计划（服务端会去重、排序并校验 `HH:MM`） |
| GET | `/api/records` | 服药记录，按「日期 + `event_seq`」去重 |
| POST | `/api/records/clear` | 清空本地记录（演示前重置用，小程序端未接入） |

服务端**没有任何鉴权**：它假设自己跑在可信局域网里。别把 `PORT` 暴露到公网。

## 数据协议

三条消息，服务 ID 统一为 `PillBox`。

**① 下发计划**（命令 `set_plan`，小程序 → 设备）

```json
{
  "service_id": "PillBox",
  "command_name": "set_plan",
  "paras": { "drug_name": "二甲双胍", "dose": "1片", "times": "08:00,12:30,19:00" }
}
```

**② 状态上报**（属性，设备 → 云）

```json
{"services":[{"service_id":"PillBox","properties":{
  "state":"idle","next_time":"19:00","weight_g":128.5,
  "lid_open":false,"taken_today":1,"total_today":3}}]}
```

**③ 服药事件上报**（属性，设备 → 云）

```json
{"services":[{"service_id":"PillBox","properties":{
  "event_seq":2,"event_drug_name":"二甲双胍","event_dose":"1片",
  "event_plan_time":"20:05","event_actual_time":"20:12","event_status":"late"}}]}
```

`event_seq` 自增，云端靠它去重；`event_status` 取 `ontime` / `early` / `late` / `missed`。

**④ 标定基准重量**（命令 `tare`，可选）

```json
{"service_id": "PillBox", "command_name": "tare", "paras": {"base_g": 130.2}}
```

设备把 `base_g`（不填则现场称一次）存为「满盒基准」，之后靠这个基准判断少了多少。
若固件采用「开机 + 每次关盖自动更新基准」（推荐做法），这条命令可以不实现，收到后回
`{"result_code": 0}` 即可。详见 `对接文档-给A.md` 第 3 节。

## 两个实现要点

**衍生签名（V11-HMAC-SHA256）**：标准版 IoTDA 实例不接受通用的 `SDK-HMAC-SHA256`，
必须用 HKDF 从 SK 派生出签名密钥，并且派生结果要转成 **hex 字符串**再作为 HMAC key。
用错算法会一直返回 `401 Authentication failed`，且错误信息不提示原因。实现见 `server/huawei.js`。

**读属性用设备影子而不是 `/properties`**：后者要求设备在线，离线直接 403。
`/shadow` 存的是最后一次上报值，设备离线也能读，小程序首页靠它渲染。

## 界面逻辑说明

首页「今日服药进度 `N / M`」：

- **分母 M** = 计划里时间点的个数（小程序掌握，始终最新）
- **分子 N** = 设备上报的 `taken_today`（设备判定完成的次数），但**只在设备最后一次上报是「今天」时才采信**
- 设备跨天没上报过时，分子按 0 计，并在计划行标注「设备今日未上报，进度按 0 计」
  —— 否则第二天打开会看到昨天残留的 `3/3`，误以为今天已经吃完
- 设备报的次数超过计划时，进度条不溢出，计划行标注「设备实报 X 次，超出计划」

## 漏服是怎么判的

设备只在**真的吃药**时上报事件（开盖 + 重量下降 ≥ 0.3g），没吃的时候它什么都不发，
所以「漏服」拿不到设备数据，只能由前端按计划推算：

> 计划里某个时间点已经过去 **30 分钟**，且当天没有 `plan_time` 与之对应的服药记录 → 判为漏服

- 首页：进度条下方红字「逾期未服 1 次：08:26（按计划推算）」，设备离线时改标注「仅供参考」
- 记录页：今天那组里补一条红色「漏服」条目，`实际时间` 显示「未记录」，底部注明这是推算值
- 实现：`miniprogram/utils/missed.js`（纯函数，`GRACE_MIN` 可调）
- 只推算**今天**，历史日期只显示设备真实上报的记录——计划可能改过，回头算历史会算错

## 事件归档为什么是轮询的

设备影子只保留**最后一次上报值**，而归档原本只在有人请求接口时才触发。
如果设备连续上报两条事件、中间没人打开小程序，前一条就被覆盖丢了。

服务端因此每 **10 秒**自己读一次影子，`event_seq` 变了就归档（两次服药不可能只隔 10 秒）。
设环境变量 `POLL_MS=0` 可关闭轮询（答辩想完全手动控制时用）。

归档日期取的是**事件的 `event_time`**，不是服务器当前时间——设备 23:59 吃药、服务器 00:01 才轮询到，
按当前时间会把记录算到第二天。

## 已知限制

- 中转服务跑在电脑上，**手机必须与电脑同一局域网**；换 WiFi 后需更新 `BASE_URL`
- 计划下发给设备后不会持久化到云端，小程序自行缓存一份
- 华为云同一设备 ID 只允许一个 MQTT 连接，控制台「在线调试」与 MQTT 客户端互斥
- 服务端无鉴权、无 HTTPS，只适合局域网演示；交付需挂到有域名的服务器上
- 服药事件靠**轮询设备影子**归档（10 秒一次），已能覆盖正常使用；但两条事件间隔小于 10 秒时前一条仍会丢。彻底解决要上 IoTDA 消息转发
- **漏服是推算值，不是设备上报**：设备离线、或根本没上报事件时，界面上仍可能显示「漏服」，底部有来源说明；它只能说明「计划时间已过且没有记录」，不能证明人真的没吃
- 计划时间点上限 **10 个**，与云端 `taken_today`/`total_today` 的 int(0~10) 对齐；排 11 次以上时设备上报会超范围，整条属性报文被平台拒收
